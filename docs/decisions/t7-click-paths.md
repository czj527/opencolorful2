## 1. 通用约定（所有链路共用）

**产物纪律（防假绿）**
- 只允许 gates §1.1 的 P1–P5 真实产物：`dist/release/<version>/` 下的桌面端安装包或 `win-unpacked/` 可执行文件（P1），且 P2–P5（版本戳四方一致、`release-manifest.json`、`SHA256SUMS.txt`、`evidence/` 原始日志）齐备、通过 `scripts/verify-release.mjs`。
- **禁止**：`pnpm dev`、未打包 `electron .`、`tsx` 直跑 `.ts`、任何 mock/fake provider 或回放；出现即命中 FG-01/FG-02/FG-03。
- 每条链路开头记录产物指纹：产物路径 + SHA256 + `gitSha`（须等于 `git rev-parse HEAD`）+ 版本号，写入账本。

**环境**
- AT-101 使用干净环境（新虚拟机 / 新用户账户 / 已按 gates F-02 清场的本机）；其余链路可用既有环境，但必须记录环境摘要（OS/arch/Node/pnpm）。
- 无有效 provider key → 相关链路判 **blocked**，**禁止**用 mock/fake 换 pass（gates §4 前置条件）。
- 数据目录与库文件（Windows 例）：`%APPDATA%\<ProductName>\state\assistant.sqlite`；macOS 例：`~/Library/Application Support/<ProductName>/state/assistant.sqlite`。
- WAL 生效判据：同目录存在 `assistant.sqlite-wal`，且 `PRAGMA journal_mode;` 返回 `wal`。

**观测命令**
- 只读 SQL：`sqlite3 "<db路径>" "<SQL>"`；无 CLI 的机器用仓内只读脚本 `node scripts/db-query.mjs "<SQL>"`。
- 表名以 `packages/state` 迁移文件为准；本文按约定名书写：`sessions` / `messages` / `memories` / `tasks` / `tool_calls` / `events`；迁移落地后命名不同时，只允许更新本节这一行。

**证据类型（每条链路 ≥1 种，鼓励叠加）**
`进程`（tasklist/ps 输出）· `文件`（产物/被写文件 + hash）· `DB行`（SQL 查询输出）· `截图`（窗口可见状态）
- **"无报错即通过"不属于证据**，一律视为缺证据。
- 四类是**观测手段**；原始输出必须落成文本日志才具证据效力（= gates P5）。

**证据存放（不新增仓内目录）**
- 根目录：`dist/release/<version>/evidence/`。
- 每条链路一份原始日志 `<链路ID>.log`：原始 stdout/stderr + exit code + 时间戳 + 机器标识。
- 截图：`<链路ID>-S<步骤号>-shot-<k>.png`（截图**不单独成立**，必须与对应 `.log` 段落并存）。
- 证据账本：`dist/release/<version>/evidence/CLICK-LEDGER.md`（格式见 §5.1）。
- 日志**只增不改**（gates §3.2：覆盖旧日志按阻塞处理）。

**GUI 操作纪律**
- 以**模拟用户**身份操作：真实点击/输入/等待渲染；禁止直接调用应用内部 API 或直接 UPDATE DB 制造"通过现象"（除 §6 AT-502/AT-503 明确要求的反例注入，且必须在被测库的**副本**上做）。
- 每步点击后 5s 内无任何 UI 反馈记为卡死（步骤内已声明为长任务者除外，需给出等待上限）。
- 执行中若发现任一 FG 迹象，立即停止并在账本标注对应 FG 编号，交 gates §3.1 定级，**不得"先跑完再说"**。

**FG 速查（发现即停，判据全文见 gates §1.2）**
FG-01 dev-only 冒充发布（进程命令行含源码路径/dev 端口、`buildTime` 晚于验收却无 `gitSha`、UI 版本显示 `0.0.0`/`dev`）· FG-02 源码直跑冒充一键可跑 · FG-03 桩/回放冒充工具调用（断网仍搜索成功、写文件未落盘、无真实 exit code）· FG-04 同进程 reload 冒充重启（PID 未变、`.sqlite`/`-wal` mtime 未变）· FG-05 版本戳/校验自证 · FG-06 门禁自证（文本"我已测过"、skip 用例、证据时间戳落在验收窗口外）· FG-07 环境残留冒充全新机器。

## 3. 链路详细步骤

### AT-101 全新机器一次跑通（总链）
**前置**：干净环境（新虚拟机 / 新用户账户 / 已按 F-02 清场）；Node 22 + corepack pnpm + git；Windows 10/11 x64 有屏；有效 provider key；唯一信息来源为仓内 `README`/`AGENTS.md`/`docs/decisions/*`（**需向实现者提问才跑通 = 文档缺陷，本次 blocked**）。
**步骤**（步骤集合 = gates §4 F-01…F-16，此处只标点击侧与证据采集点）
1. S1 执行 F-01 记录环境摘要；执行 F-02 清场断言（截图或命令输出证明 `%APPDATA%`/`%LOCALAPPDATA%` 无应用数据、无 `node_modules`、无 `.sqlite` 残留）。
2. S2 执行 F-03 记录 `git rev-parse HEAD`；F-04 `pnpm install --frozen-lockfile`；F-05 `pnpm build`；F-06 `node scripts/verify-release.mjs dist/release/<version>`，要求输出 `VERIFY-OK <version> <gitSha>`。
3. S3 F-07 安装/解包产物并**从系统入口启动**：桌面窗口出现、输入框可用（截图）。
4. S4 F-08 版本戳四方比对（UI 内显示 / 根 `package.json` / 产物文件名 / `git tag`），四处全等。
5. S5 依次走 §4 串联脚本（覆盖 F-09…F-13）。
6. S6 F-14 一键命令（文档声明的唯一入口，见 AT-102）exit 0 并生成 `evidence/` 日志；F-15 文档节制检查（`README` + `AGENTS.md` + `design.md` + `docs/decisions/t1…t7` 齐备且与实现一致）。
7. S7 F-16 汇总 verdict 交 gates（本文件不判定）。
**预期证据**：F-01–F-16 每步的命令 + 输出 + exit code（落 `AT-101.log`）；产物路径 + SHA256；启动后进程；关键界面截图。
**失败即阻塞**：任一 F 步非 0 退出；需口头补步骤；出现 dev/源码直跑/手工建库；`VERIFY-OK` 缺失或 sha256 不符。

### AT-102 一键可跑
**前置**：AT-101 S2 已产出真实产物；已确认文档声明的唯一入口命令（`pnpm start` 类）或双击 exe 两种形态中的**文档声明那一种**。
**步骤**
1. S1 从文档抄录"一键"命令原文，并核对它确实存在于根 `package.json` scripts（或为产物 exe）。
2. S2 冷启动该入口（先确认无残留应用进程）。
3. S3 观察窗口出现、输入框可聚焦，输入一句问候并发送成功。
4. S4 等待应用完全退出，记录该命令的 exit code。
5. S5 确认 `dist/release/<version>/evidence/` 下已由该次运行生成日志。
**预期证据**：`进程`（启动后 PID）；`截图`（窗口 + 首条输入成功）；`文件`（命令原文 + exit code + 生成的日志文件）。
**失败即阻塞**：命令不在 scripts 中却宣称"一键"（FG-02）；需手工干预（先手工 `pnpm build`、手工建目录、手工设环境变量）才算跑通；exit code 非 0。

### AT-103 版本戳与校验
**前置**：`dist/release/<version>/` 已存在 `release-manifest.json` 与 `SHA256SUMS.txt`（gates P2–P4）。
**步骤**
1. S1 读取 UI 关于页/`app.getVersion()` 显示的版本号（截图）。
2. S2 读取根 `package.json` 的 `version` 与产物文件名的版本号。
3. S3 执行 `git tag --points-at HEAD` 与 `git rev-parse HEAD`，比对 `release-manifest.json.gitSha`。
4. S4 现场重算产物 sha256，与 `SHA256SUMS.txt` 逐行比对。
5. S5 执行 `node scripts/verify-release.mjs dist/release/<version>`，记录 `VERIFY-OK <version> <gitSha>` 行。
**预期证据**：`文件`（比对输出 + `VERIFY-OK` 行 + 重算 sha256）。
**失败即阻塞**：四处版本任一不等（FG-05）；重算 sha256 与清单不符；`gitSha` ≠ `rev-parse HEAD`；`buildTime` 早于最后一次提交（陈旧产物）。

### AT-201 聊天主循环
**前置**：AT-101 启动完成；数据目录为空或已知（首次启动应自动建库）。
**步骤**
1. S1 记录当前 `session_id`（新建对话时的会话 ID）与进程 PID。
2. S2 输入 `你好，请回复一句话确认在线`，点击发送（或 Enter）。
3. S3 观察流式输出：首 token 5s 内出现，逐字/逐块追加，结束后输入框恢复可用。
4. S4 滚动会话历史，确认本轮问答在界面上。
5. S5 DB 查询：`select id, session_id, role, length(content), created_at from messages order by created_at;`
**预期证据**：`DB行`（S5，含助手回合，`session_id` 与 S1 一致）；`截图`（S3 流式过程 + S4 完整历史）。
**失败即阻塞**：首 token > 5s 或全程无流式（一次性整段出现且无增量刷新）；发送后无任何 UI 变化；助手回合未落库或 `session_id` 不一致。

### AT-202 多轮上下文
**前置**：AT-201 通过；同一会话不刷新、不重启。
**步骤**
1. S1 在 AT-201 的同一会话追问 `请复述我刚才说的第一句话`。
2. S2 确认回复正确引用上一轮内容。
3. S3 再补一轮多行文本，确认上下文不串行、历史顺序正确。
4. S4 DB 查询该会话全部 `messages`，核对 `session_id` 唯一且顺序正确。
**预期证据**：`DB行`（两轮以上同一 `session_id`，顺序与界面一致）；`截图`（追问回答）。
**失败即阻塞**：追问答非所问或依赖界面缓存而非库内历史；新一轮产生新 `session_id`（等于偷换会话）。

### AT-301 读文件
**前置**：AT-201 通过；工作目录已知；预置一个内容已知的只读样本文件（记录其内容与 sha256）。
**步骤**
1. S1 新开会话，输入 `请读取 <工作目录>/agentplant-sandbox/sample.md 并原样告诉我内容`，发送。
2. S2 确认界面出现读取类工具卡片（工具名可见），状态 running → success。
3. S3 核对回复内容与样本文件逐字一致。
4. S4 DB 查询该次工具调用，核对路径参数与返回体。
**预期证据**：`文件`（样本内容 + sha256 前后一致）；`DB行`（`tool_calls` 中读取调用，路径正确、`status='success'`）；`截图`（工具卡片 + 回复）。
**失败即阻塞**：回复内容与文件不符（编造内容 = FG-03）；无 `tool_calls` 行却给出内容。

### AT-302 写文件
**前置**：AT-301 通过；工作目录可写。
**步骤**
1. S1 输入 `请在 <工作目录>/agentplant-sandbox/hello.md 写入三行：plant / assistant / 2026，然后读回给我看`，发送。
2. S2 确认出现写入工具卡片，状态 running → success。
3. S3 在文件管理器中定位该文件并打开，确认 3 行内容正确。
4. S4 记录文件 `mtime`、size、sha256（须落在本次运行时间窗内）。
5. S5 DB 查询写、读两次调用均 `success`。
**预期证据**：`文件`（路径 + 内容 + `mtime` + sha256）；`DB行`（write/read 各 1 行）；`截图`（工具卡片）。
**失败即阻塞**：文件不存在或内容/mtime 与回复不符（FG-03）；无 `tool_calls` 行；写入越出工作目录且未被沙箱拦住（记录为治理风险）。

### AT-303 执行命令
**前置**：AT-302 通过；shell 工具可用、沙箱初版生效。
**步骤**
1. S1 输入 `执行一条命令，把当前时间写入 <工作目录>/agentplant-sandbox/now.txt`，发送。
2. S2 确认命令工具卡片显示**实际命令原文**。
3. S3 确认卡片显示**真实退出码**（应为 0）与 stdout/stderr。
4. S4 打开 `now.txt` 核对时间戳与系统时间误差 < 5 分钟。
5. S5 DB 查询该次调用：命令行、`exit_code`、`status`。
**预期证据**：`DB行`（`exit_code=0`、`status='success'`、命令原文）；`文件`（`now.txt` 内容）；`截图`（命令卡片含 exit code）。
**失败即阻塞**：只有"执行成功"文本而无真实 `exit_code`（FG-03）；命令越出工作目录（沙箱未生效）。

### AT-304 网页浏览/搜索
**前置**：AT-201 通过；机器可联网（记录网络可用性证据）。
**步骤**
1. S1 输入 `搜索 "<一个可验证的固定查询词>"，打开第一条结果，把页面标题和 URL 告诉我`，发送。
2. S2 确认出现搜索工具卡片，随后出现抓取/浏览工具卡片。
3. S3 打开浏览视图（或外部浏览器已打开的该 URL），人工核对标题与 URL。
4. S4 将界面显示的标题/URL 与 DB 中工具返回体逐字比对，记录工具调用/请求 ID。
5. S5（反证，可选但推荐）断网后重发同一请求，确认**失败**而非"成功"（排除 FG-03）。
**预期证据**：`DB行`（搜索与抓取各一条，返回体非空 + 请求 ID）；`截图`（页面 + 工具卡片）。
**失败即阻塞**：返回体为空却给出标题/URL（编造）；回复与返回体不一致；断网仍"成功"（FG-03）。
**网络影响**：间歇失败按 gates §3 定级（严重），本文件不判定。

### AT-401 记忆写入
**前置**：AT-201 通过。
**步骤**
1. S1 输入 `请记住我的偏好：咖啡不加糖，且我常用工作目录是 <路径>`，发送。
2. S2 确认回复表示已记录；如在记忆面板可见则一并截图。
3. S3 DB 查询 `select id, kind, content, created_at from memories order by id desc limit 5;`
4. S4 记录本次写入的 `memories.id`（后续 AT-402/AT-403 必须命中同一 id）。
**预期证据**：`DB行`（≥2 行，含"不加糖"与工作目录路径）；`截图`（回复 / 记忆面板）。
**失败即阻塞**：仅聊天文本声称"已记住"而 `memories` 无对应行；内容被改写或关键信息丢失。

### AT-402 跨会话召回
**前置**：AT-401 通过（已记录 `memories.id`）；**不重启进程**。
**步骤**
1. S1 点击"新建对话"，确认会话列表出现第二个会话，记录新 `session_id`（必须 ≠ AT-201 的 `session_id`）。
2. S2 在新会话输入 `我的咖啡偏好是什么？`，发送。
3. S3 确认回答包含"不加糖"，且界面出现记忆检索工具卡片。
4. S4 DB 核对：两个 `sessions` 行存在；新会话的检索调用命中 AT-401 记录的同一 `memories.id`。
**预期证据**：`DB行`（≥2 个 `session_id` + 命中同一 `memories.id`）；`截图`（新会话问答 + 会话列表）。
**失败即阻塞**：答对但无任何检索调用（疑似上下文泄漏或硬编码）；命中 id 与 AT-401 不一致；"新会话"实为同一 `session_id`。

### AT-403 重启不丢
**前置**：AT-302 / AT-401 / AT-402 全部通过；已记录重启前快照。
**步骤**
1. S1 记录重启前三项事实：`messages` 行数、`memories` 行数、`hello.md` 的 sha256。
2. S2 记录当前进程 PID、`.sqlite` 与 `-wal` 的 mtime、`PRAGMA journal_mode`。
3. S3 **完全退出**：通过应用退出菜单/关窗并等待自行退出（不得 kill 进程冒充）。
4. S4 确认进程已消失（无残留后台进程），日志中记录退出码。
5. S5 从**同一发布产物**重新启动，记录新 PID（必须 ≠ S2）。
6. S6 确认会话列表自动恢复，打开原会话可见历史问答。
7. S7 新会话提问 `你还记得我的咖啡偏好和我刚才写的文件吗？`，确认回答含"不加糖"。
8. S8 重新查询三项事实与 `hello.md` sha256，与 S1 比对；核对库文件未被重建（创建时间不变、`memories.id` 不变）。
**预期证据**：`进程`（前后 PID 不同 + S4 空结果）；`DB行`（前后计数/`memories.id` 一致 + `journal_mode=wal`）；`文件`（`hello.md` sha256 前后一致）；`截图`（S6 历史 + S7 回答）。
**失败即阻塞**：PID 未变或 `-wal` mtime 未变（FG-04）；库被重建、旧行消失、`memories.id` 变化；重启后会话列表为空；删除候选记忆后重启仍能召回（种子/缓存，FG-04）。

### AT-501 SQLite 单库 + WAL
**前置**：应用已完成至少一次运行（已有 `messages`/`memories` 数据）。
**步骤**
1. S1 定位运行时状态目录，列出全部与状态相关的文件（记录 `*.sqlite`、`-wal`、`-shm`）。
2. S2 确认**只有一个** `.sqlite` 文件，且任务/会话/记忆三域同库（在其中一个库内 `select name from sqlite_master where type='table';` 能看到三域表）。
3. S3 执行 `PRAGMA journal_mode;` 返回 `wal`；执行 `PRAGMA wal_checkpoint;` 观察不报错。
4. S4 检查仓库与产物目录：无 `*.sqlite`/`.env` 入仓（`git status` 干净），无 Redis/MQ/JSON 旁路状态文件。
5. S5 确认无第二个运行时状态存储进程（记录 `进程` 列表）。
**预期证据**：`文件`（文件列表 + `git status`）；`DB行`（`journal_mode` 与 `sqlite_master` 输出）；`进程`（无 Redis/MQ）。
**失败即阻塞**：存在第二个运行时状态存储；未开 WAL；三域不同库；`*.sqlite` 入仓。

## 4. 主链路端到端串联（一遍过，串行脚本）

> 一次运行、一份账本、不中途修环境。**任一步证据缺失即在此停手**；不得跳过前序链路、先跑后段再回头补证据。
> 前置：AT-101 + AT-102 + AT-103 已通过（否则先跑这三条）。

1. **E1** 启动发布产物（记录版本 + sha256 + `gitSha` + PID）→ 执行 **AT-201** S1–S5。证据写 `evidence/AT-201.log`。
2. **E2** 执行 **AT-202** S1–S4（多轮上下文，仍同一 `session_id`）。证据写 `evidence/AT-202.log`。
3. **E3** 执行 **AT-301** S1–S4（读样本文件）。证据写 `evidence/AT-301.log`。
4. **E4** 执行 **AT-302** S1–S5（写/回读 `hello.md`，记录 sha256）。证据写 `evidence/AT-302.log`。
5. **E5** 执行 **AT-303** S1–S5（写 `now.txt`，核对真实 exit code）。证据写 `evidence/AT-303.log`。
6. **E6** 执行 **AT-304** S1–S5（搜索 + 抓取 + 断网反证）。证据写 `evidence/AT-304.log`。此步失败不阻断后续链路，但必须在账本标记并交 gates §3 定级。
7. **E7** 执行 **AT-401** S1–S4（写入偏好记忆），记录 `memories.id`。证据写 `evidence/AT-401.log`。
8. **E8** 执行 **AT-402** S1–S4（新会话召回，核对命中同一 `memories.id`）。证据写 `evidence/AT-402.log`。
9. **E9（重启点 RST-1）** 记录 S1 快照 → **完全退出并确认进程消失** → 用同一产物重新启动 → 执行 **AT-403** S6–S8。证据写 `evidence/AT-403.log`。
10. **E10** 执行 **AT-501** S1–S5（单库 + WAL 断言）。证据写 `evidence/AT-501.log`。
11. **E11** 执行 **AT-502…AT-506**（§6 治理脚本）。证据写 `evidence/AT-502.log` … `AT-506.log`。
12. **E12** 汇总 `CLICK-LEDGER.md`（§5.1），逐链路核对"步骤数 ≤ 证据行数"，自检 CP-01…CP-05，交 gates §4 F-16 判定。

串联硬约束：
- RST-1 之前禁止升级/重装产物；RST-1 之后禁止改动 DB 文件、禁止删除 `-wal`。
- 全程禁止手工改库；唯一例外是 §6 AT-502/AT-503 的反例注入，必须在**库副本**上做或事后回滚并在账本声明。
- 任一步命中 FG-01…FG-07 → 停止串联，按 gates §1.2 判 blocked，不得"改天补证据"沿用本次 verdict。

## 5. Agent 执行者协议

### 5.1 证据账本格式（唯一一份：`dist/release/<version>/evidence/CLICK-LEDGER.md`）

| 链路ID | 步骤号 | 证据类型 | 存放位置 | 采集时间 | 观测结论 |
|---|---|---|---|---|---|
| AT-302 | S3 | 文件 | `dist/release/2026.9.0/evidence/AT-302.log` 内 `S3` 段落 + `AT-302-S3-shot-1.png` | 2026-09-11 10:16:02 | 文件存在，3 行，sha256=… |
| AT-302 | S5 | DB行 | 同上 `AT-302.log` 内 `S5` 段落 | 2026-09-11 10:16:20 | write/read 各 1 行，status=success |

必填规则：
- 六列全填；`存放位置` 必须是**可被他人直接打开的路径**，不接受"见截图"这类指代。
- 证据类型必须落在 `进程/文件/DB行/截图` 四类内；**文本自述不算证据**；截图必须与对应 `.log` 段落并存。
- 同一截图不得复用登记到多个步骤；每步独立采集。
- 每步至少 1 行证据；18 条链路全覆盖，不接受抽样代替。
- 账本与日志只增不改（gates §3.2）。

### 5.2 "进度文本≠交付"落地检查点（本链路强制自查）

- **CP-01（AT-301/AT-302/AT-303）**：回复出现"我接下来要创建/执行…"而当轮**无 `tool_calls` 行且目标文件不存在**时，该步骤记为未交付，不得以文本判定完成。
  检查动作：把"文本声称的动作"与"`tool_calls` 行 + 文件系统结果"逐条配对，两者必须同时成立。
- **CP-02（AT-401）**：回复声称"已记住/已保存"但 `memories` 无对应行 → 未交付；唯一交付凭据是 `memories.id`，文本仅作参考。
- **CP-03（AT-403）**：重启后回复声称"我记得"但库中无对应行 → 未交付；反过来说库中有行而界面未恢复 → 同样未交付（两侧都要成立）。
- **CP-04（AT-201/AT-202）**：以"正在思考/稍等，我马上回答"之类文本收尾而无助手回合落库 → 未交付；流式必须可见完成态。
- **CP-05（账本自查）**：账本中出现"待补证据 / 我接下来会补 / 见上文"或空 `存放位置` → 该链路整体未完成，交 gates 前必须补齐；进度说明不得入账本充数（FG-06）。

## 6. P0 治理演示脚本（AT-502…AT-506）

> 数据准备：用一次真实运行（§4 E1–E7）产生 `tasks`/`messages` 数据。反例注入仅限库**副本**或演示后回滚，并在账本声明。
> 每条 ≤5 步，且必须有 gates §2.1 要求的 metadata-only 审计事件旁证（只记事件元数据，不得记正文/参数）。

**AT-502 CAS 领取（并发双 claim，恰一成功）**
1. 造一条 `pending` 任务（UI 新建或 `insert`），记录 `id`。
2. 第一次领取：`update tasks set status='running', claim_token='<A>' where id='<id>' and status='pending';` 记录 `changes()` 与 token。
3. 第二次领取（模拟另一执行者，不重置状态）：`update tasks set status='running', claim_token='<B>' where id='<id>' and status='pending';` 记录 `changes()`。
4. 在应用侧触发同一任务的第二次领取路径，观察是否收到"已被领取"类显式冲突反馈。
5. 读终态：`select id,status,claim_token from tasks where id='<id>';` + 截图 + 审计事件。
**判定**：S2 `changes()=1`、S3 `changes()=0` 且 token 仍为 `<A>`；第二个执行者收到显式冲突、**无重复执行**。两次都成功或第二次静默改 token → 不成立。

**AT-503 终态不可降级**
1. 取一个终态任务：`select id,status from tasks where status in ('completed','failed') limit 1;`（无则先跑完一个任务）。
2. 在**库副本**上注入回退：`update tasks set status='running' where id='<id>';`
3. 读取结果：`select changes();` 与 `select id,status from tasks where id='<id>';`
4. 在 UI 打开该任务详情，观察状态显示（截图）。
5. 收集拒绝报错原文 + 审计事件。
**判定**：`changes()=0`（或被触发器/CHECK 以**显式报错**拒绝，非静默忽略），状态仍为终态，UI 不回退。`changes()=1` 且变为 `running` → 不成立。

**AT-504 进度文本≠交付**
1. 发送一个会触发工具的任务（如 `写一个文件 <dir>/g504.txt`）。
2. 在工具**尚未成功**的时刻记录界面文本与时间戳（可能出现"我接下来要…"）。
3. 此刻查询 `select count(*) from tool_calls where status='success' and ...;` 与目标文件是否存在。
4. 记录该时刻任务状态（应为 blocked/needs_input，**不得** completed）与审计事件，并确认未消耗重试限额。
5. 归集证据（截图 + DB行 + 文件存在性）。
**判定**：纯进度文本不得成为完成依据，正确落到 blocked/needs_input 且不消耗重试限额。若 Agent 不产出进度文本，则人工注入一条纯进度文本消息并验证其**不产生**完成态（同样取证）。

**AT-505 三层限额**
1. 读取限额配置（生成深度 / 子任务数 / 并发 lane）并记录配置来源路径与值。
2. 并发 lane：连续快速发送 2 条消息，观察是"第二条排队"还是并行处理（截图 + `messages` 时间戳）。
3. 子任务数：触发第 N+1 个子任务创建（N=配置上限），观察是否被拒并给出**显式错误**。
4. 生成深度：构造达到 depth 上限的请求，观察拒绝行为。
5. 记录三份拒绝报错 + 审计事件，并标注每层"已演示 / 未实现"。
**判定**：超限必须显式拒绝且拒绝事件入审计；不得静默截断或静默降级后仍宣称成功。任一层未实现 → 记 `N/A` 交 gates 裁定，执行者不得自评通过。

**AT-506 子权限不超父**
1. 确认当前运行形态（MVP 单 Agent）。
2. 优先走点击链路：发一条要求越权（超出父权限范围）的请求，观察是否**显式报错**且**不静默降级**。
3. 若单 Agent 下无法构造点击场景，按 gates §2.1 改用**单元级证据**：运行越权用例测试并把 stdout/stderr + exit code 落 `AT-506.log`。
4. 记录显式报错原文（或测试输出）与审计事件。
5. 在账本中标注所用证据形态（点击 / 单元级）。
**判定**：越权必须显式报错、不静默降级为受限执行还宣称完成；单元级证据允许按 gates §2.1 替代点击链路，但**必须**含 exit code，不得只给"已通过"文本（FG-06）。
